# Repo Create（建仓规范：权限先问，落盘齐备）

## 身份与使命

每次创建远端 git 仓库，**先评估内容、再友好询问可见性、最后才创建**。公开/私有不是默认值，而是基于仓库内容的决策；同时确保 LICENSE 与 README 不是缺项（配合 repo-license / readme-author）。

## 工作流

### 第 1 步：内容评估（先于一切）

扫描仓库内容（目录、README、代码、配置、样本数据），按 [references/content-assessment.md](references/content-assessment.md) 分类：

- **可公开（public-safe）**：通用工具/库/插件、教程与示例、无敏感信息的个人作品；
- **敏感（sensitive）**：密钥/凭据、内网地址、客户或用户数据、商业逻辑、未授权第三方资产、个人隐私；
- **模糊（ambiguous）**：内部工具、半成品、公司项目、含少量敏感线索。

### 第 2 步：给出推荐 + 友好询问（不要机械）

基于评估结果，用**一句话说明理由 + 一个默认推荐**向用户询问，让用户一句话就能确认或改：

- 可公开内容 → 推荐**公开**：说明"内容是通用插件/库，公开有利于分享与协作"；
- 敏感内容 → 推荐**私有**：点明发现了什么敏感信号（如 `.env`、密钥、内网地址），建议清理或私有；
- 模糊内容 → 摆出取舍：公开=曝光与协作，私有=安全与未完成；给一个倾向，但把决定权交给用户。

询问措辞要友好、像人话（模板见 [references/content-assessment.md](references/content-assessment.md) 的"询问话术"），禁止冷冰冰的"公开还是私有？"二选一弹窗。

### 第 3 步：按答复创建

- GitHub：`POST /api.github.com/user/repos`，`private: true|false`；
- Gitee：`POST /api/v5/user/repos`，`private: true|false`；
- 本地 `git init` 后 add remote → push（凭据策略：HTTPS 持久化或 SSH，见机器既有配置）。

### 第 4 步：落盘三件套自查

- [ ] **权限**：与用户确认的可见性一致（创建后用 API 复核 `private` 字段）；
- [ ] **LICENSE**：存在且合适（见 repo-license 技能）；README 有 License 链接；
- [ ] **README**：达标（见 readme-author 技能；至少 tagline + 安装 + 快速开始）。

## 决策规则

| 内容信号 | 推荐 | 理由话术 |
|---|---|---|
| 通用库/插件/工具、无敏感信息 | 公开 | "内容是通用组件，公开利于分享、协作与收录" |
| 含 `.env`/密钥/令牌/内网 URL/客户数据 | 私有 | "检测到敏感内容（列出具体），建议先清理或保持私有" |
| 内部工具、半成品、公司项目 | 问清再定 | "内部工具公开会暴露实现细节；半成品公开会留下坏印象" |
| 个人作品/教程（明确想分享） | 公开 | "教程/示例公开能帮助更多人" |
| 拿不准 | 询问，默认倾向私有 | 安全优先，之后可一键转公开 |

铁律：

- **绝不静默默认公开**（隐私/商业风险），也**绝不静默默认私有**（扼杀开源分享）——先问。
- **敏感信号优先**：发现敏感内容时，即使"大概率想公开"也要先提示。
- **询问必须带理由和推荐**，不能是无脑二选一。
- 创建后**复核实际权限**，与答复一致。

## 边界

- 不替用户做可见性决定：推荐可以给，最终选择权在用户。
- 不做穷尽式密钥扫描（那是安全审计工具的活），但必须拦下**明显**敏感信号并提示。
- 不扫描远程内容（仓库已存在时只按用户描述与本地文件判断）。
- 用户明确说"不用问，直接公开/私有"时，尊重其指令并记下偏好，下次同类内容可少问。

## 反面清单（Anti-patterns）

- 建仓不问权限，默认 public（最常见的隐私事故来源）。
- 建仓不问权限，默认 private（个人想开源却被锁死）。
- 问了但没给理由和推荐（机械弹窗，增加用户负担）。
- 建完才发现 `.env`/密钥进了公开仓库（应先审后建）。
- 权限确认了但创建时写错 `private` 字段（必须复核）。
- 只看仓库名猜内容，不看仓库实际内容就下结论。

## 复查循环

1. 内容评估做了吗？敏感信号列出来了吗？
2. 询问给了理由 + 推荐吗？用户确认了吗？
3. 创建的 `private` 字段与确认一致吗（API 复核）？
4. LICENSE / README 齐了吗（引用 repo-license / readme-author）？
