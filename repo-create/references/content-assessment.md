# 仓库内容评估与可见性询问

## 一、内容分类信号表

评估仓库内容时逐项核对；命中任一"敏感"信号即按敏感处理，命中多个"可公开"信号可放心推荐公开。

### 可公开（public-safe）信号

- 通用工具/库/插件/CLI（不绑定特定公司内部环境）
- 教程、示例代码、模板、学习笔记
- 无密钥、无凭据、无真实用户数据
- 许可证明确（MIT/Apache 等宽松协议）
- 作者明确表达分享意图（如 README 写"欢迎使用/贡献"）

### 敏感（sensitive）信号（任一命中即拦截）

- 密钥/令牌：`.env`、`*.pem`、`id_rsa`、API key、`gho_`/`npm_`/`sk-` 等格式字符串
- 内网地址：`192.168.x.x`、`10.x.x.x`、`localhost` 之外的内部域名、公司 VPN
- 客户/用户数据：真实手机号、身份证、邮箱列表、数据库导出、埋点数据
- 商业逻辑：未公开的定价、算法、供应链、内部系统名
- 未授权第三方资产：他人版权素材、破解工具、内部文档
- 个人隐私：证件照、家庭地址、聊天记录

### 模糊（ambiguous）信号

- 内部工具（命名含公司/团队名，或 README 面向内部）
- 半成品（TODO 密集、无 README、无测试）
- 公司项目（repo owner 是公司账号，或含公司版权声明）
- 仅含少量敏感线索（单个测试密钥、单个内网 URL）

## 二、询问话术模板（友好、带理由与推荐）

### 可公开内容 → 推荐公开

> 看下来这个仓库是通用插件/工具，没有密钥或内部信息——公开的话方便分享、协作和以后被收录。我建议**公开**，可以吗？还是你想先私有？

### 敏感内容 → 推荐私有（并点名信号）

> 我发现仓库里有 `.env`（含 `xxx` 密钥）和 `192.168.x.x` 内网地址，直接公开会泄露敏感信息。建议先**私有**，等清掉敏感内容再转公开。要不要我顺手把敏感文件加进 `.gitignore`？

### 模糊内容 → 摆取舍

> 这个仓库像是内部工具/半成品：公开能拿到反馈，但也会暴露实现细节（或留下未完成的第一印象）；私有则更安全，等完善了再公开也不迟。我倾向**私有**，你说了算？

### 用户已有明确偏好

> 明白，按你的来——**公开**。下次同类（通用组件、无敏感信息）我直接按公开建，不再重复问。

## 三、平台 API 可见性参数

| 平台 | 创建接口 | 参数 |
|---|---|---|
| GitHub | `POST https://api.github.com/user/repos` | `private: true\|false`（默认 false） |
| Gitee | `POST https://gitee.com/api/v5/user/repos` | `private: true\|false`（默认 false） |
| GitLab（自建） | `POST /api/v4/projects` | `visibility: private\|internal\|public` |

创建后复核：GitHub `GET /repos/{owner}/{repo}` → `private` 字段；Gitee `GET /api/v5/repos/{owner}/{repo}` → `private` 字段。

## 四、权限转换（事后补救）

- GitHub：`PATCH /repos/{owner}/{repo}` `{ "private": true }`（公开转私有会清空 fork/star 部分元数据，先提醒）；
- Gitee：`PATCH /api/v5/repos/{owner}/{repo}` `{ "private": true }`。
- 若敏感内容已进公开仓库：先转私有 → 清理历史（filter-repo）→ 轮换凭据 → 再决定是否重新公开。
